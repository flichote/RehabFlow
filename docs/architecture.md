## 2. 设计原则

| 原则 | 说明 |
| :--- | :--- |
| **状态机驱动** | 患者状态与课程状态是系统的灵魂，所有业务动作通过统一状态转换入口（`tracking` 服务）执行，禁止散落到处改状态 |
| **软打卡替代硬件** | 位置由业务动作推导（开始/结束上课），不依赖蓝牙信标；人工修正走审计 |
| **冲突检测必须事务化** | 排课写入在数据库事务 + 行锁内完成，杜绝并发脏写 |
| **权限在服务端强制** | 前端只做 UI 隐藏，后端按角色 + 行级数据过滤 |
| **读写分离策略** | 排课高频读走 Redis，写穿更新；看板聚合查询走数据库（低频） |

## 3. 模块边界与职责

### 3.1 核心模块（★ = V2 核心）

| 模块 | 职责 | 关键不变量 |
| :--- | :--- | :--- |
| `scheduling` 排课引擎 | 创建/修改/取消课程、拖拽排课接口、双重冲突检测 | 同一患者/康复师在同一时间区间不得有两节冲突课程 |
| `courses` 课程执行 | 开始上课、结束上课、治疗记录、课时计算 | 开始时间=实际开始，结束时间=实际结束；未点开始超时→异常 |
| `tracking` 软打卡 | 患者状态机、位置推导、自动巡检（30min 未结束提醒） | 位置变更必有审计记录（patient_status_log） |
| `notifications` 提醒 | 新课程/变更/课前15min/超时5min/评估待办 | 每个触发事件有模板，可追溯发送记录 |
| `alerts` 预警 | 异常生成、主任看板实时推送、处理闭环 | 预警必须可标记处理，处理后从看板消失 |
| `dashboard` 看板 | KPI/分布/工作量/趋势聚合 | 刷新频率分级：实时 / 30min / 每日 |

### 3.2 支撑模块

| 模块 | 职责 |
| :--- | :--- |
| `auth` | 注册/登录/JWT/角色守卫 |
| `patients` | 患者档案 CRUD、360° 聚合查询 |
| `assessments` | 评估量表记录、趋势查询 |
| `rooms` / `therapists` | 治疗室与康复师资源管理 |

## 4. 关键机制设计

### 4.1 排课冲突检测（事务化）

```text
POST /api/v1/courses  （创建课程）
  BEGIN TRANSACTION;
    SELECT ... FROM courses WHERE patient_id=? AND status NOT IN ('已完成','未完成-*')
      AND start_at < :new_end AND end_at > :new_start FOR UPDATE;   -- 患者冲突锁
    SELECT ... FROM courses WHERE therapist_id=? AND status NOT IN ('已完成','未完成-*')
      AND start_at < :new_end AND end_at > :new_start FOR UPDATE;   -- 康复师冲突锁
    IF 任一命中 → 返回冲突明细（冲突课程列表），事务回滚
    ELSE → INSERT course；COMMIT
```

- **时间重叠判定**：`start_at < new_end AND end_at > new_start`（半开区间）。
- **FOR UPDATE 行锁**：防止两个管理员并发排同一时段。
- **强制替换**：允许场景（管理员显式选择），删除被替换课程并写审计。

### 4.2 软打卡状态机（tracking 服务）

```text
动作源（唯一入口）：
  ① 康复师开始上课 → 课程=进行中；患者=治疗中；位置=对应治疗室
  ② 康复师结束上课 → 课程=已完成；患者=在病房；位置=病房
  ③ 医生手动修正   → 患者状态/位置按表单更新（写审计）
  ④ 定时巡检任务   → 课程结束30min后仍"治疗中"→ 推送康复师确认

实现：
  - patient_status_log 表记录每次变更（from→to, actor, occurred_at）
  - 状态变更通过统一 service 方法 transition(patient, to_status, ctx)
  - 看板/360° 位置卡实时读取"最近一条状态日志"
```

### 4.3 提醒与预警（事件驱动）

```text
触发源：
  - 排课成功/变更/取消 → notifications（站内信 + 浏览器通知）
  - 定时任务（cron）：
      ├─ 课前 15min 扫描 → 发送上课提醒，课程状态→提醒已发，患者→前往途中
      ├─ 课程超时 5min 未开始 → 提醒康复师/医生 + 生成 alert
      └─ 课程结束 30min 巡检 → 提醒康复师确认是否忘点结束
  - 康复师标记缺席 → 生成 alert
  - 冲突未处理（强制替换被拒）→ 生成 alert

推送通道（按可用性降级）：
  站内信（必须） → 浏览器 Notification API（Web） → 短信（可选扩展，待 PRD §9 决策）
```

### 4.4 数据权限隔离（服务端强制）

| 角色 | 数据范围 |
| :--- | :--- |
| 医生 doctor | `Patient.doctor_id = current_user.id` |
| 康复师 therapist | `Course.therapist_id = current_user.id`；患者=名下患者 |
| 管理员 admin | 全量 |
| 患者 patient | 本人 |

> 实现：查询层统一注入 scope（SQLAlchemy query filter），不允许业务代码裸查全表后过滤。

### 4.5 缓存策略

| 数据 | 策略 | 失效时机 |
| :--- | :--- | :--- |
| 排课日历（周/日视图） | Redis，key=`sched:{therapist_or_group}:{date}` | 任何课程写操作 → 删除相关 key（写穿） |
| 今日概览 KPI | Redis 短 TTL（30s） | TTL 自然过期 |
| 患者当前状态 | 不缓存（低频 + 需实时） | — |

## 5. 部署拓扑（docker-compose，规划）

```text
┌─ docker-compose ─────────────────────────────┐
│  frontend (Next.js)    :3000  → 后端 API 代理 │
│  backend  (FastAPI)    :8000  → PG + Redis    │
│  postgres (16)         :5432                 │
│  redis                 :6379                 │
└──────────────────────────────────────────────┘
```

- 开发期：backend 可切 SQLite 零依赖起步（与 CCN 同策略，留 PG 切换口）。
- 生产：nginx 前置 + HTTPS；后端多 worker（uvicorn `--workers 4`）；PG 持久卷。

## 7. 安全与合规要点

1. JWT 密钥环境变量注入，永不入库/入前端。
2. 所有写操作走审计（audit_log），排课/位置/预警三类必须。
3. 患者数据是医疗敏感数据：接口统一行级权限，禁裸查询。
4. 浏览器通知需用户显式授权；短信通道若接入需合规授权（TBD）。

## 8. 架构决策记录（ADR 摘要）

| # | 决策 | 理由 |
| :--- | :--- | :--- |
| ADR-1 | 冲突检测用数据库事务 + FOR UPDATE 而非应用层锁 | 多实例部署下应用锁不可靠 |
| ADR-2 | 位置不存单表，用状态日志最近一条推导 | 天然带审计，支持"何时到哪"查询 |
| ADR-3 | 排课读走 Redis 写穿，不用消息队列 | 规模下不需要 MQ，保持简单 |
| ADR-4 | 提醒先用站内信 + 浏览器通知，短信延后 | 短信成本 + 合规待定（PRD §9） |
| ADR-5 | 定时任务用 APScheduler 进程内，约束单实例 backend | 避免引入 Celery 复杂度；后续如需可换 |
